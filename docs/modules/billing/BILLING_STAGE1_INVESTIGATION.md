## 2. Pre-Existing Backend Procedures

The following procedures were already established:
1. `activate_subscription_addon(...)` — Activates an add-on, records payment ledger row, and supersedes previous active records.
2. `deactivate_subscription_addon(...)` — Immediately cancels an active add-on.
3. `cancel_company_subscription(...)` — Schedules or executes subscription cancellation with remarks and feedback.
4. `get_company_subscription_details(...)` — Fetches current subscription plan, add-ons, and payment history.

## 4. Key Architectural & Security Requirements

1. **Add-on Lifecycle Management**:
   - Marking an add-on as `cancelling` keeps it operational until its paid period ends (`ended_at`), then stops renewal.
   - Reactivation reverts `cancelling` back to `active` if `NOW() < ended_at`.
   - Dedicated atomic routines replace client-side `for` loop updates.
2. **Quota & Usage Counter Concurrency**:
   - `usage_counters` are upserted authoritatively using unique `(company_id, limit_key)`.
3. **Plan Configuration Authority**:
   - `plan_features` sync must be atomic single-transaction (update primary or insert, prune legacy duplicates).
4. **OAuth Phone Backfill**:
   - Safe tenant-checked atomic routine to synchronize phone into `shared.users` and `shared.profiles`.
